# Day 2 · Return Values, Expressions, and Loops

Day 1 ended on the difference between a statement and an expression. Today that one distinction does most of the work: it decides what a function returns, it lets `if` sit on the right-hand side of a `let`, and it lets `break` carry a value out of a loop.

Then the day ends somewhere else entirely. A `for` loop destroys an array, the identical loop over numbers does not, and the explanation has nothing to do with loops.

> Today's code: [`day2/variables/`](https://github.com/RoddyH17/rust_learn/tree/main/day2/variables) · Notes and rubric: [`day2/NOTES.md`](https://github.com/RoddyH17/rust_learn/blob/main/day2/NOTES.md)

## The semicolon that changes what a function returns

A return type goes after an arrow, and the return value is the **last expression, written without a semicolon**:

```rust
fn five() -> i32 {
    5           // no semicolon — this is the return value
}

fn main() {
    let x = five();
    println!("The value of x is: {x}");
}
```

`let x = five();` is the same as `let x = 5;`. The body is a lonely `5` because that is the expression whose value we want.

Which brings up the rule that explains most of today's compiler errors:

- **no semicolon = expression** — it has a value
- **semicolon = statement** — its value is `()`

So this fails, and the reason is one character:

```rust
fn sum(x: i32, y: i32) -> i32 {
    x + y;      // the `;` makes the body return (), not i32
}
```

You can also return early with the `return` keyword, and *that* form does take a semicolon. The way I wrote it in my notes: `return` comes with a semicolon; no `return` means no semicolon.

A function with no `->` returns `()`. If it only prints, that is exactly what you want.

## `if` is an expression too

```rust
fn main() {
    let condition = true;
    let number = if condition { 5 } else { 6 };

    println!("The value of number is: {number}");
}
```

Blocks evaluate to their last expression, and a bare number is an expression, so the whole `if` has a value and can sit on the right of a `let`. The catch: **both arms must have the same type**, because `number` gets exactly one type and the compiler has to know it without running the program.

```rust
let bad = if condition { 5 } else { "six" };  // error
```

## Loops, ranges, and labels

Ranges follow the same left-closed, right-open convention as everything else in Rust, with `..=` as the inclusive form:

```rust
for n in 1..4  {}           // 1, 2, 3
for n in 1..=4 {}           // 1, 2, 3, 4
for n in (1..=4).rev() {}   // 4, 3, 2, 1
```

To get the index as well, use `.enumerate()` rather than a manual counter:

```rust
for (i, v) in [4, 3, 2, 1].iter().enumerate() {
    println!("element {} is {}", i + 1, v);
}
```

The manual version works:

```rust
let a = [10, 20, 30, 40, 50];
let mut index = 0;

while index < 5 {
    println!("the value is: {}", a[index]);
    index += 1;
}
```

— but it is error-prone. Change the array to four elements and forget to update the condition and it panics. It is also slower, because the compiler has to emit a bounds check on every single iteration to make sure the index is still inside the array. A `for` loop over the collection itself cannot go out of range at all, so there is nothing to check.

`loop` is an expression, so `break` can carry a value out:

```rust
let result = loop {
    counter += 1;
    if counter == 10 {
        break counter * 2;   // result == 20
    }
};
```

**This works only in `loop`.** `for` and `while` cannot break with a value, because neither is guaranteed to reach the `break` at all — so there would be no value to produce when the loop ends normally.

Labels start with a single quote and let an inner loop break the outer one:

```rust
'counting_up: loop {
    loop {
        if count == 2 { break 'counting_up; }  // leaves BOTH loops
        break;                                 // leaves the inner one
    }
    count += 1;
}
```

## The loop that eats your data

This was the real lesson of the day, and it is not a loop feature at all — it is ownership showing up early, disguised as syntax.

```rust
let v = vec![1, 2, 3];
for element in v {
    println!("{element}");
}
println!("{:?}", v);   // error: v was moved into the loop
```

`for x in collection` **takes the collection**. After the loop, it is gone. The fix is one character:

```rust
for element in &v { }        // borrow it instead
```

and if you want to change the elements while walking them, borrow mutably and dereference:

```rust
let mut v = vec![1, 2, 3];
for element in &mut v {
    if *element == 1 {
        *element = 5;
    }
}
```

What makes this genuinely confusing is that the identical code with a plain array of numbers works:

```rust
let numbers = [1, 2, 3, 4];
for n in numbers { }
println!("{:?}", numbers);  // fine
```

`i32` implements `Copy`, so `[i32; 4]` is `Copy` too, and the array is *copied* into the loop while the original stays untouched. A `Vec` is never `Copy` — copying one would mean either two `Vec`s pointing at the same heap block, which is a double free waiting to happen, or a silent deep copy with hidden cost. Rust refuses both, so a `Vec` can only move.

Same syntax, opposite outcome, and the only thing that decides it is whether the type is `Copy`.

The three forms are worth memorising as a set:

| Written as | Desugars to | Each item is | Collection afterwards |
|---|---|---|---|
| `for x in &v` | `v.iter()` | `&T` | usable |
| `for x in &mut v` | `v.iter_mut()` | `&mut T` | usable, and modified |
| `for x in v` | `v.into_iter()` | `T` | **consumed** — unless the element is `Copy` |

`for e in &v` and `for e in v.iter()` are exactly the same thing; the first is sugar for the second. (One historical footnote worth knowing when reading old code: before Rust 1.53, `for e in array` gave you references. It gives you values now.)

The practical rule: **write `&` by default**, unless you actually mean to consume the collection.

That last table is the whole argument for ownership in one example — and it is exactly where Day 3 starts.
